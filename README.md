# AI 工程流水线（ai-eng-pipeline）

> 把一句口语化的需求，走成一套**可验收、可追溯、可回滚**的交付物。
> 支持软件 / 硬件 / 人力资源三个领域，不绑定任何 AI 平台。

---

## 它解决什么问题

AI 已经能写代码了，但大多数人交付不了项目。原因不是模型不够强，是**流程缺了三样东西**：

1. **没有验收标准** —— 做完了才想"怎么算做对"，于是设计出一个刚好能过的测试
2. **误差逐级累积** —— 串行 5 个环节，每环 10% 理解偏差，终点偏差约 41%，而且不知道是哪一环引入的
3. **审查是假的** —— 让同一个 AI"站在审查者角度看看"，它会替自己找理由，永远说通过

这三条不修，AI 越强，你越容易交付一个**看起来很完整、实际不能上线**的东西。

## 它怎么修

| 问题 | 解法 |
|---|---|
| 没有验收标准 | **可验证性前置**：验收标准写在方案之前，写完即冻结 |
| 误差累积 | **产物落盘**：下游只读文件，不读上游的推理。文件是锚点 |
| 审查是假的 | **盲审隔离**：审查者在独立上下文，只拿三个文件，拿不到作者的思路 |
| 一律开全套流程太重 | **规模裁剪**：S 级小改直接做，不开流水线 |
| 一个流程套所有领域 | **两段式**：先定领域与验证方式，再开始干活 |

## 一个真实的对照实验

本仓库带了一个端到端案例（`tests/t5/`）：一个 Markdown 表格转 CSV 的小工具，6 条验收标准。

| 轮次 | 审查方式 | 结论 |
|---|---|---|
| 第 1 轮 | `unblinded` 自审 | P0=2，修复 |
| 第 2 轮 | `unblinded` 自审 | **PASS**，8 个单元测试全绿 |
| 第 3 轮 | `blinded` 独立子代理 | **FAIL，P0=2 P1=3** |

第 3 轮抓出的两个 P0，都是第 2 轮放过的：

- 分隔行判定过宽，把只含 `-`/`:` 的**数据行**误判为分隔行**静默跳过** → 数据丢失
- 非 UTF-8 文件触发 `UnicodeDecodeError`，直接崩溃并打印堆栈

而当时 `unittest` 显示 `Ran 8 tests ... OK`。这就是"假的绿"——测试全过，代码是坏的。

**同一个实现，自审说没问题，盲审说不能交付。** 这就是为什么 I4（审查必须隔离）是不变量。

## 两段式：先定标准，再干活

```
Stage 0  判领域 → 读领域包 → 写 00b-领域实例 → G0 → 用户确认
Stage 1+ 拆需求 → 定验收 → 出方案 → 排路径 → 产出 → 独立盲审 → 交付
```

Stage 0 存在的理由：**同一个流程套到不同领域，失败原因完全不同。**

- 软件失败在边界与编码
- 硬件失败在热、EMC、公差累积
- 人力资源失败在合法性与可考核性

拿"缺少单元测试"去审一份人力资源制度，是正确的废话。所以必须先定标准。

## 快速开始

```bash
git clone <repo>
cd ai-eng-pipeline

# 建一次运行
python scripts/init_run.py "帮我做个把 Markdown 表格转成 CSV 的工具" --domain software --root .

# 门禁机械校验
python scripts/check_run.py run-YYYYMMDD-NN --stage g1

# 版本与提交
python scripts/bump.py --run run-YYYYMMDD-NN --type feat --scope build --message "..." --commit
```

然后让你的 AI 读 `SKILL.md`（WorkBuddy / Claude Skill）、`AGENTS.md`（Codex / Cursor / 通用）或 `PROMPT.md`（ChatGPT 类网页版）。

```
ai-eng-pipeline/
├── SKILL.md                  主流程（WorkBuddy / Claude Skill 入口）
├── AGENTS.md                 通用入口（Codex / Cursor / Gemini CLI）

├── references/
│   ├── core/                 ★ 内核：不变量、契约、门禁、判级、领域实例化、盲审
│   ├── domains/              领域包：software / hardware / hr / _template
│   └── roles/                5 个角色卡（lead/spec/architect/builder/reviewer）
├── scripts/                  init_run / check_run / bump
└── assets/templates/         8 份产物空壳
```

## 9 条不变量

这是整个项目的地基。**任何领域、任何版本、任何平台都不能变。**

`I1` 原文不可改写 · `I2` 产物必须落盘 · `I3` 可验证性前置于方案 · `I4` 审查必须隔离
`I5` 门禁是布尔判断 · `I6` 每份产物有字数上限 · `I7` 迭代≤3 轮且升级留痕
`I8` 编排层不产出实质内容 · `I9` 一个事实只写一处

领域包只能填变量（怎么验证、交付什么、攻击哪里），不能改这九条。
详见 `references/core/invariants.md`。

## 加一个新领域

**两条路，先分清要哪条：**

**A. 沉淀成领域包**（这个领域你会反复用）

1. 复制 `references/domains/_template.md` 为 `references/domains/<domain>.md`
2. 填 8 个槽位（交付实体 / 验证方式 / 方案载体 / 攻击面 / 角色映射 / 合规 / 判定用语 / 判级门槛）
3. 确认没有违反任何不变量
4. 在 `references/core/stage0-instantiate.md` 的信号表里加你的关键词

不需要改任何核心文件。这是领域可插拔的意义。

**B. 一次性陌生领域**（这个领域你可能只做一次）

不要建领域包。走 `references/core/domain-discovery.md`：

1. 判 `domain: custom`
2. 三级通道取证（用户材料 / 联网检索 / 模型知识只产问题），证据分 E0-E3
3. 写 `00c-领域取证.md`（证据台账 / 未取证清单 / 架构适配假设 / 取证能力声明）
4. 按 `00b` 的槽位填，但槽位 2/4/6/7 必须引 `[EV-xx]`
5. 过 G0.9 才能进 Stage 1

**为什么要有 B 这条路**：编造的行业规范、公差等级、合规条款不会有任何东西报错 ——
软件里编造的 API 会被 import 拦下，建筑里编造的 GB 号会一路走到施工。
E3（模型自身知识）被强制显性化成"待确认问题"，是这条路上唯一的防线。

## 版本策略

| 变更 | 版本位 |
|---|---|
| 改了任意一条不变量 / 改了产物编号 | **MAJOR** |
| 新增领域包 / 新增产物字段 / 新增门禁项 | MINOR |
| 措辞、示例、错别字 | PATCH |

领域包自带 `version` 和 `requires_core`，可以独立演进。

## 已知局限

1. **真盲审依赖平台有子代理能力。** 没有时只能降级并如实标注，G3 会一直判否。这是刻意的诚实。
2. **语义判断脚本查不了。** `check_run.py` 只保证"结构上没得抵赖"，需求是否合理靠人。
3. **S 级不开流水线**，小任务的隐患只有自检一层。
4. **字数上限偏紧**，复杂方案可能被卡（目前无附录豁免机制）。
5. **效果强依赖模型遵循度**，弱模型会把门禁当建议。
