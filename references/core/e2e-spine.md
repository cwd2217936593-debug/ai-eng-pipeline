# 全链路主脊（E2E Spine）

> **作用**：定义"从头到尾"里的"头"和"尾"，防止实际执行从中间开始、到中间结束。
> **产物**：`08-追溯矩阵.md`。
> **门禁**：G2.10（声明覆盖方式）、G3.8（矩阵闭合）。

---

## 为什么需要它

"从头到尾全做"这句话如果没定义头尾，会稳定地退化成：

```
从需求开始（因为需求是第一条能看见的东西）
到"能跑起来"结束（因为这是第一个能证明自己的时刻）
```

这个退化非常自然，没有人会觉得自己在偷工。但结果是：
- 需求从哪来的？没人问（可能是用户随口一句，也可能背后有真实工况）
- 坏了谁修？没人管（交付即失联）
- 现场装不进去？设计阶段不知道（没做过装配可达性）

**上游缺失**会让设计建立在一个没被验证的前提上；
**下游缺失**会让设计在最容易翻车的地方没有预案。

两者都不会在任何门禁上显示为红 —— 因为门禁只检查"有没有做，做得对不对"，
不检查"该做的范围是不是全"。

所以需要一份显式定义范围的东西。

## 八层（L0–L7）

| 层 | 名称 | 核心问题 | 产物 | 门禁 |
|---|---|---|---|---|
| **L0** | 场景与工况 | 在什么条件下活着？ | `00d`（SC→OP→DC） | G0.10 |
| **L1** | 需求与验收 | 要什么？怎么算做对了？ | `01` `02` | G1 |
| **L2** | 总体方案 | 整体怎么搭？关键取舍是什么？ | `03` 系统级 | G2 |
| **L3** | 分系统 / 模块 | 各部分职责与接口 | `03` 分节 或 `03a` | G2 |
| **L4** | 详细设计 | 材料/尺寸/公差/参数/接口细节 | `03` 详细节 或 `03a` | G2 |
| **L5** | 实现与制造 | 真做出来 | `05` | G3 |
| **L6** | 验证与试验 | 证明它做对了 | `06` + 试验记录 | G3 |
| **L7** | 交付与运维 | 交给谁、坏了怎么办 | `05` 交付说明 / `09` | G3.8 |

### 每层的"跳层后果"

| 跳过 | 后果 | 实际事故形态 |
|---|---|---|
| L0 | 设计建立在未验证前提上 | 按室内设计，装在室外，一年锈穿 |
| L2 | 只有一个方案，没有取舍 | 出事时无法回答"为什么不用另一个" |
| L3 | 模块职责重叠或漏 | 两个模块都以为对方在做，结果没人做 |
| L4 | 参数是经验值 | 公差累积超差，装配干涉 |
| L5 | 只有设计没有实物 | 交付物是 PPT |
| L6 | 没证明做对了 | "应该没问题" |
| L7 | 交付即失联 | 现场坏了，没有备件、没有排查路径、没人知道设计意图 |

**L7 是最常被跳的一层，也是用户感受最直接的一层。**

一个冷库支架交付后，两年后螺栓锈断 —— 如果 L7 里有"维护检查项：每年检查紧固件锈蚀，
更换周期 5 年"，这次失效是可预防的。没有 L7，它就是"意外"。

## 允许合并，不允许跳过

这是本文件最重要的一条规则。

| 级别 | L2–L4 怎么放 | 最低要求 |
|---|---|---|
| **S** | 合并为 `03` 里的三小节 | 三节都要有，每节 ≥3 行实质内容 |
| **M** | `03` 里 L2 一节 + L3/L4 各一节 | 每层至少一个可判定的设计决策 |
| **L** | `03`（L2/L3）+ `03a-详细设计.md`（L4） | L4 每个关键件有参数表 |

**"合并"意味着写在一处但仍要写到；"跳过"意味着不写。**
判断标准：追溯矩阵里该层的单元格是否有实质内容（含数字、编号、专名）。

S 级合并的合法示例：
```
### 3.2 方案（含 L2/L3/L4）
L2 总体：单文件 CLI，输入 md 输出 csv，无外部依赖。
L3 模块：读取层（编码探测）、解析层（表格扫描）、写出层（CSV 转义）。
L4 细节：转义仅处理 \| 与 \\；行分隔用 \r\n|\r|\n 正则；编码优先 utf-8-sig。
```

不合法的"合并"：
```
### 3.2 方案
用 Python 写一个转换脚本，处理边界情况。
```
（L2 没取舍，L3 没模块，L4 没参数 —— 这不是合并，是省略。）

## 追溯矩阵：五列两向

`08-追溯矩阵.md` 的全部内容就是一张表加一段统计。

| 场景参数 | 需求 R | 设计特征 DF | 验证 AC | 证据 |
|---|---|---|---|---|
| OP1 -40℃ | R1 螺栓材料 | DF1 材料选 A4-70 | AC1 低温冲击 | 报告-001 |
| OP3 95%RH 凝露 | R2 防腐 | DF2 钝化 + 蜡封 | AC2 盐雾 480h | 报告-002 |

### 上行闭合（防"拍脑袋需求"）

```
每条 DF  →  能追到某条 R
每条 R   →  能追到某个 SC/OP（或明确标 [假设] 并挂 A#）
```

追不到 SC/OP 的 R 叫**无源需求**。它不是错的，但它必须说明来源：
要么是用户明确提的（`00` 有原话），要么是法规要求的（挂 RULE），
要么是设计师自己加的（**必须标 `[假设]` 并进 `00d` 假设表**）。

无源需求是范围蔓延的入口。今天加一条"顺便也支持一下"，明天加一条，
最后没人知道为什么在做这些。

### 下行闭合（防"漏验"）

```
每条 R   →  至少有 1 个 DF 实现它
每条 DF  →  至少有 1 条 AC 验证它
```

没有 DF 的 R 叫**空头需求**（答应了没做）。
没有 AC 的 DF 叫**未验设计**（做了但没证明）。

**未验设计是最危险的一类**，因为它看起来完成了。
"我加了防松垫圈"—— 但没人验证过它在 -40℃ 还有效。

### 第三向：参数溯源（防"经验值"）

```
每个带单位的数字  →  追到 OP（算出来的）/ RULE（标准规定的）/ A#（假设）
```

这一条专门对付"公差 0.1""裕量 20%""周期 3 天"这类数字。
它们看起来是专业判断，实际上常常是**从上一个项目抄来的**，
而那个项目的场景可能完全不同。

## 五类孤儿（必须为 0）

| 类型 | 定义 | 检查 | 处置 |
|---|---|---|---|
| **孤儿需求** | R 无 DF 实现 | 下行扫描 | 补实现，或删需求并记 `07` |
| **孤儿设计** | DF 无 R 支撑 | 上行扫描 | 补需求（说明为什么加），或删设计 |
| **未验设计** | DF 无 AC 验证 | 下行扫描 | 补 AC（回 G1，作废受影响判据） |
| **无源参数** | 数字无 OP/RULE/A# 出处 | 逐数字扫描 | 补出处，或降级为假设 |
| **孤儿场景** | OP 无 DC 也没 R 承接 | 从 L0 往下扫 | 补设计约束，或确认该 OP 不影响设计并记理由 |

**第五类（孤儿场景）最容易漏，也最伤**：它是反向的漏。
前四类都是"做了但没依据/没验证"，第五类是"看见了但没管"。

一个真实的例子：场景里写了"最高环境温度 60℃"，但设计里没有任何一条约束、也没有一条需求提到温度。
这个 OP 就白写了 —— 它出现在文档里，制造了"我们考虑过温度"的假象，实际什么都没发生。

**处置方式与"孤儿需求"不同**：孤儿场景不一定要补需求。
如果这个 OP 确实不影响设计（例如"海拔 100m"，在设计上等价于常压），
在矩阵里写明"OP6 不影响设计：海拔低于 1000m 无需修正"即可，不必硬造一条 R。

**允许带裁决交付**：五类孤儿若有 `07` 的 `D#` 裁决（说明为什么这次不修、代价是什么），
可以放行，但交付结论必须标"带缺陷交付"，且 `08` 的明细列要写该 `D#`。
没有裁决的孤儿，一律判否。

**实践中很难一次全 0。**第一遍扫出 10–20 个孤儿是正常的，处置过程本身就是设计收敛。
真正的问题不是有孤儿，是**没扫过**。

## 与两段式的关系

```
Stage 0（元设计）
  L0 场景        ← 必须先于一切（I11）
  ↓
Stage 1+（施工）
  L1 → L2 → L3 → L4 → L5 → L6 → L7
```

L0 单独在前，因为它是**约束的源头**。其余七层是链条，顺序不能乱（下游只读上游文件，I2）。

一个常见的错误：把 L0 当成 L1 的一部分（"场景写进需求文档里"）。
这会导致场景变成需求的注脚 —— 而实际上需求是场景的推论。
**顺序错了，权重就错了。**

## 一句话

> 全链路不是"多做几步"，是**让每一步都能被上下两头夹住**。
> 上有场景约束，下有验证兜底，中间的设计才不是悬空的。
