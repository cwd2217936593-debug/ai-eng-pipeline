# 编排协议（ORCHESTRATION）

> 这份文件把 lead 从"一个人"变成一个**可被任何平台执行的调度器**。
> 目标：多 AI **自动启动、自动分派、自动回收**，而不是靠人手动跑每一步。

---

## 1. 为什么需要单独一份协议

角色卡（`roles/*.md`）写的是"每个角色做什么"，但没写"**谁、在什么条件、启动谁、传什么、回收什么**"。

这导致一个问题：换一个平台（WorkBuddy → Claude Code → ChatGPT），启动子代理的方式完全不同，
于是"自动启动"退化成了"人照着文档手动点"。**流程对，但没人自动跑。**

编排协议把"调度"这件事也落成契约，让调度本身可复现、可校验、不依赖具体平台。

---

## 2. 一个统一的调度循环（所有平台通用）

```
loop:
  1. 读当前状态（哪些产物已落盘、哪个门禁该判）
  2. 找出"输入齐了、还没做"的下一步
  3. 启动对应角色（子代理 / 单轮提示词），只传它有权读的文件
  4. 回收产物，判门禁
  5. 门禁过 → 进入下一步；门禁否 → 带失败项退回
  6. 累计偏移 >1.0 或 3 轮不过 → 停，升级裁决
```

每一步的"启动条件"只取决于**文件是否存在 + 门禁是否通过**，不取决于"人记不记得做"。

---

## 3. 每一步的启动条件与交接物（核心表）

| 步 | 角色 | 启动条件（输入齐） | 传入文件 | 产出文件 | 完成判据（门禁） |
|---|---|---|---|---|---|
| S0 | lead | 00 存在 | 00 | 00a, 00b | I0.0/I0.1 + G0 |
| S0b | lead | 00b 冻结 | 00, 00b, 领域包 | 00e | I12（澄清非空） |
| S0c | 领域专家 | 00e 非空 | 领域包, 00e, 00d | 00f | I12（复核非空） |
| S1 | spec | 00e/00f 齐 + G0 过 | 00, 00e, 00f, 00d | 01, 02 | G1 |
| S2 | architect | G1 过 | 01, 02, 00d | 03, 04 | G2 |
| S3 | builder | G2 过 | 03, 04, 02 | 05 | 自查 |
| S4 | reviewer | 05 存在 | 05, 02, 00, 00d | 06, 08 | G3 |

**两条铁律**：
1. **传入文件 = 该角色角色卡第 1 节"我读哪些文件"**，一个都不许多传，一个都不许少传。
2. **启动 = 传文件 + 一句"读 X 写 Y"**，不传上一棒的对话记录（I2：对话是流沙）。

---

## 4. 平台适配（同样的循环，不同的"启动"实现）

| 平台 | "启动角色"怎么实现 |
|---|---|
| WorkBuddy / Claude Code | 起子代理（Agent），传文件路径 |
| ChatGPT（无子代理） | 一段自包含提示词：`读这些文件 → 写这个文件 → 返回`，人工贴 |
| DeepSeek / 其他 | 同 ChatGPT，单轮或少量多轮 |

> 关键：**无论平台能力高低，调度循环不变，变的只是"启动"这一行的实现**。
> 平台能起子代理 → 真并行/真隔离；不能 → 串行 + 明示降级（不许假装隔离）。

---

## 5. 调度器自己怎么被校验（防止"编排也漂"）

1. **每步完成判据是布尔门禁**，不是"我觉得做完了"。
2. **交接物只走文件**，调度器不能"口头补充"上一棒没写进文件的话。
3. **调度器不产出内容**（I8）：它只判断"该启动谁"，不替角色写。
4. 若调度器判断"该回 Stage 0"，它必须能指出**累计偏移分超阈值**或**门禁具体哪条否**，
   不许用"感觉不对"当理由。

---

## 6. 一句话

**角色卡管"做"，编排协议管"谁做、什么时候做、拿什么做"。
两者都落成文件契约，多 AI 才能真的自动跑起来，而不是靠人肉接力。**
