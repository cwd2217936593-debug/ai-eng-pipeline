# 意图主线锚点 + 偏移度量（INTENT ANCHOR）

> 这是整套流程里**最上游、优先级最高**的机制，对应不变量 **I0**。
> 它回答一个所有门禁都回答不了的问题：**我们最后做出来的，还是不是用户最初要的那个？**

---

## 1. 为什么单独需要它

门禁（G0–G3）查的是**内部一致性**：需求有没有来源、方案有没有覆盖验收、实现有没有证据。
它们**查不了"方向对不对"**——因为方向错误在内部看是自洽的。

多 AI 协作的真正风险不是"某一棒写错了"，而是**每一棒都忠实执行了上一棒的交接物，但意图在交接中一点点稀释**：
spec 把"转 csv 别搞坏转义"理解成"转 csv"；architect 把"转 csv"实现成"支持多格式"；
builder 交付了一个能转十种格式的工具——每一棒都对，最后产品不是用户要的。

**这根尺子，量的就是"离最初意图多远"。**

---

## 2. 锚点怎么提炼（Stage 0 做）

由 lead 在 Stage 0 结束时，从 `00-原文.md` 提炼，写入 `00a-意图主线.md` 的「锚点」段。

提炼规则（三要三不要）：

**要：**
1. 一句话说清「用户要解决的**问题**」，不是「要做的东西」。
2. 用用户的词，不用你的术语。
3. 写清「成功的标志是什么」（用户凭什么说"对了"）。

**不要：**
1. 不要出现技术方案、工具名、实现细节（"用 Python"就偏了）。
2. 不要写多条——就一条。多条意味着你还没想清楚，或者是把需求写进来了。
3. 不要写"做一个 XX"这种名词短语——那是交付物，不是问题。

**正反例：**

| | 锚点写法 | 判定 |
|---|---|---|
| ✅ | 用户要的是"把带竖线转义的 Markdown 表格可靠地转成 CSV，转义不能坏" | 问题 + 成功标志，无方案 |
| ❌ | 做一个高效的 Markdown→CSV 命令行工具 | 是交付物描述，不是问题 |
| ❌ | 1. 支持转义 2. 支持命令行 3. 处理错误 | 三条 = 把需求抄进来了 |

---

## 3. 偏移打分怎么打（每棒交接时做）

每个角色在**读完上一棒交接物、动手之前**，先回答一个问题：

> 我理解的"主线"是什么？和 `00a` 里的锚点，是同一条吗？

若不同，打偏移分。用 0–1 连续值：

| 偏移分 | 含义 | 处置 |
|---|---|---|
| 0 | 完全对齐，我做的事就是锚点那件事 | 正常继续 |
| 0.1–0.3 | 局部偏离（扩了范围/换了个说法），但不影响主线 | 记录，继续，在「主线回指」里注明 |
| 0.4–0.6 | 明显偏离（理解成了另一件事） | **停下**，把理解写出来回给 lead，要求对齐 |
| 0.7–1.0 | 完全偏了（做的是无关的东西） | **停下**，本次产物作废，回 Stage 0 重对齐 |

**累计规则**：5 棒（spec/architect/builder/reviewer/lead 汇总）各自的偏移分累加，总和 > 1.0 → 判定"主线已漂移"，必须回 Stage 0 重提炼锚点，而不是继续往下修。

> 偏移分不是给产物打质量分，是给"这一棒有没有守住主线"打分。质量分交给门禁，方向分交给这里。

---

## 4. 主线回指（每个产物的头部一行）

`01`–`08` 每个产物头部必须有一行：

```
主线回指：本产物服务于锚点「……」（偏移分 0.2：额外覆盖了多表情况，属范围扩展，不影响主线）
```

规则：
- 回指必须能对上 `00a` 的锚点原文，不能是"我服务于用户的需求"这种空话。
- 偏移分必须写，0 也要写 0。
- 回指写不出来（不知道自己在服务什么）→ 判偏移，门禁拦截。

---

## 5. 机械检查

`check_run.py` 校验：
1. `00a-意图主线.md` 存在，「锚点」段非空。
2. `01`–`08` 每个头部有「主线回指」行。
3. 回指行为空 / 写"无" / 不含偏移分数字 → 判否。
4. 累计偏移分（从各产物回指里提取）> 1.0 → 判否，提示"回 Stage 0 重对齐"。

---

## 6. 和现有机制的关系（不重复）

| 机制 | 守什么 | 什么时候拦 |
|---|---|---|
| I1 原文 | 用户**说了什么** | 原文被改写时 |
| **I0 锚点** | 用户**要什么** | 方向偏了时 |
| G0–G3 门禁 | 产物**内部自洽** | 格式/来源/证据缺时 |
| 偏移打分 | 每棒**离主线多远** | 累计漂移时 |

四层各守一层，不重叠。门禁再全，也守不住方向——那正是 I0 的职责。

---

## 7. 反例：这套机制自己怎么被绕过

- **把锚点写得跟需求一样具体** → 等于把 I1 重抄一遍，失去"问题层"的抽象，起不到靶心作用。
- **每棒偏移分都填 0** → 机械检查只能抓"填没填"，抓不了"填得诚不诚实"。所以偏移分必须配合 I4 盲审：reviewer 的职责之一就是**独立复核前几棒的偏移分是否合理**。
- **锚点写太宽**（"用户想做好这个项目"）→ 宽到谁都回指得上，等于没有。锚点要窄到"偏了能被看出来"。

> 最后一个反例最关键：锚点的价值在于**它窄**。宽锚点不会错，但也拦不住任何东西。
