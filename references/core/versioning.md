# 版本策略（versioning.md）

> 本文件说明这个项目怎么版本化，以及**为什么版本不是"改了就加个号"**。

## 为什么版本重要

这套东西不是软件库，是**规程**。规程的版本乱掉，比代码版本乱掉更危险 ——
因为下游所有基于它产出的交付物（需求、验收、审查结论）都失去了可比性。

典型事故：同一个项目，三周前用 v1 的验收标准，三周后用 v2 的，然后发现标准变了，
但没人知道是哪一条变的、为什么变。此时"这个交付物合不合格"已经无法回答。

所以：**版本号必须能回答"哪条规矩变了"**。

## 三个层级

| 层级 | 版本在哪 | 谁改它 |
|---|---|---|
| **内核**（不变量/契约/门禁/角色） | `VERSION` 文件 | 维护者 |
| **领域包** | 各 `domains/*.md` 的 frontmatter `version` | 领域维护者，可独立演进 |
| **单次运行** | `run-*/VERSION` + git commit | `scripts/bump.py` 自动 |

## 内核版本（MAJOR.MINOR.PATCH）

| 变更 | 位置 | 例子 |
|---|---|---|
| **MAJOR** | 不变量增删改、产物编号重排、门禁语义反向 | 删掉 I4（审查隔离）→ 3.0.0 |
| **MINOR** | 新增领域包、新增产物字段、新增门禁项、新增角色 | 加 `domains/finance.md` → 2.1.0 |
| **PATCH** | 措辞、示例、错别字、排版 | 改一个反例写法 → 2.0.1 |

**判据一句话**：如果这次改动会让"昨天的运行结果按今天的规矩重判不过"，就是 MAJOR。

## 领域包版本

领域包自带两个字段：

```yaml
version: 1.0.0            # 领域包自身版本
requires_core: ">=2.0 <3.0"   # 兼容的内核范围
```

规则：
- 领域包可以有自己的迭代节奏，不影响内核版本
- 但 `requires_core` 必须真实 —— 内核升到 3.0 时，所有领域包要重新验证是否仍兼容
- **领域包不得覆盖不变量**。如果某个领域确实无法满足某条，必须在 `00b` 声明豁免 + 降级，而不是在领域包里偷偷改规则

## 单次运行版本

`scripts/bump.py` 维护：
- `run-*/VERSION`：本次交付的语义版本
- `CHANGELOG.md`：每次变更的意图可读记录
- git commit：真正的可回滚保障

**注意**：`bump.py` 只负责"说清楚改了什么"，真正的回滚靠 git。
让 AI"负责版本控制"只会得到一个编造的版本号，那是假的安全感（见 I2 与 C6 的历史教训）。

## 提交信息规范

```
<type>(<scope>): <subject>
```

| type | 用在 |
|---|---|
| `feat` | 新增能力（新领域包、新产物字段） |
| `fix` | 修正错误（门禁误判、契约矛盾） |
| `docs` | 措辞、示例 |
| `refactor` | 结构调整（不改语义） |
| `chore` | 脚手架、脚本 |

`breaking change` 必须在 body 里写 `BREAKING CHANGE:` 并说明迁移方式。

## 发布检查单

升 MAJOR 前必须确认：

- [ ] `CHANGELOG.md` 写清"哪条不变量/哪个编号变了"
- [ ] 所有领域包的 `requires_core` 已更新
- [ ] 旧版运行目录是否还能被新版 `check_run.py` 读（能读则给兼容说明，不能读则明确废弃）
- [ ] `README.md` 的"12 条不变量"清单与实际一致
- [ ] 打 tag：`git tag -a v2.0.0 -m "..."`

最后一条经常被忘：**没有 tag 的版本号只是文件里的一个字符串。**
