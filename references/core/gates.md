# 门禁（gates.md）

四道门禁，全部是**布尔判断**。禁止出现"较好""基本满足""大致符合""基本可用"——无法判真假的评语本身即判 `否`。

顺序：**G0 领域 → G1 需求 → G2 方案 → G3 交付**。
G0 是 2.0 新增，位置在一切之前：领域判错，后面全废。

判定方式只有两种：**机械**（`scripts/check_run.py` 或命令输出）、**取证**（能在文件里定位到具体行）。凭印象判 `是` 视为伪造门禁，一旦发现，本次交付作废。

> **判"是"之前先过 `anti-bypass.md` 的门禁自检三问。**
> 特别是第三问：我在读产物之前是不是已经知道答案了。答"是"即为确认偏误，该条判否。

## G0｜领域门禁（Stage 0 → Stage 1）

进入条件：`00b-领域实例.md` 已写。

| ID | 判断句（真/假） | 判定方式 | 证据位置 |
|---|---|---|---|
| G0.1 | `domain` 是 `software`/`hardware`/`hr`/`custom` 之一 | 机械 | `00b` 头部字段 |
| G0.2 | 判定依据引用了用户原话或具体信号词（≥1 处） | 取证 | `00b` 判定依据段 |
| G0.3 | 5 个通用角色都有映射，且 `reviewer` 与 `builder` 不是同一角色 | 取证 | `00b` 角色映射表行数 = 5 |
| G0.4 | 交付实体说得清放什么文件、给谁用（能落到 `05`） | 取证 | `00b` 交付实体段 |
| G0.5 | 验证方式含「手段 + 执行者 + 反馈周期」三样，周期有具体量级 | 取证 | `00b` 验证方式段 |
| G0.6 | 攻击面 ≥5 条，且是本领域特有（非照抄其他领域） | 人工比对 + 机械计数 | `00b` 攻击面列表 |
| G0.7 | `豁免声明` 与 `domain` 一致（如 `hr` 不得空着合规项） | 取证 | `00b` 豁免段 |
| G0.8 | 用户已确认（`07` 有 Stage 0 的确认记录，或对话中有明确"对"） | 取证 | `07` / 对话 |

**全 `是` → 进入 Stage 1（spec）。**

**任一 `否` → 退回 Stage 0 重写 `00b`。** 不许带未确认的领域实例开工 —— 这是整套流程里最便宜的一次返工。

**特别注意**：G0.3 与 G0.6 是最容易糊弄的两条。角色映射少一个（通常是 reviewer）意味着少一道校验；攻击面照抄软件的五条意味着领域包根本没起作用。这两条必须人工核对，不能只看"有没有填"。

### G0.10｜场景门禁（与 G0 并行，任一不过都停）

进入条件：`00d-场景工况.md` 已写。参考 `scenario.md`。

| ID | 判断句（真/假） | 判定方式 | 证据位置 |
|---|---|---|---|
| G0.10.1 | SC1–SC8 八槽位都有具体值（`N/A` 必须带理由） | 机械 + 取证 | `00d` §2 |
| G0.10.2 | OP ≥3 行，每行有数值 + 单位 + 来自哪个 SC | 机械 | `00d` §3 |
| G0.10.3 | DC ≥3 行，每行挂 `RULE-`/`EV-`（纯项目自定约束可挂 `SC#`，但数值型不行） | 机械 | `00d` §4 |
| G0.10.4 | 每条 DC 有落点 DF（材料/尺寸/公差/工艺/接口） | 取证 | `00d` §4 末列 |
| G0.10.5 | 假设表每行四列齐：依据等级、若错代价**及方向**、谁确认、返工点 | 机械 | `00d` §5 |
| G0.10.6 | 假设数 ≤ 该级别上限（S=2/M=5/L=8） | 机械 | `00d` §5 + `07` 判级 |
| G0.10.7 | 场景标签已给出（四域组合） | 取证 | `00d` §2 末行 |
| G0.10.8 | 用户已确认场景（`07` 有记录） | 取证 | `07` / 对话 |

**全 `是` → 与 G0 一并放行。任一 `否` → 回 Stage 0 补 `00d`。**

**G0.10.5 的"方向"为什么必填**：偏保守和偏冒险是两种完全不同的错。
偏保守是花钱（可以接受，要让人知道），偏冒险是出事（必须解决）。
只写"若错会返工"等于没说 —— 返工的方向决定了这条假设能不能带着走。

**G0.10.6 为什么要有上限**：假设超限说明需求根本没聊清楚。
继续做出来的是一份漂在 8 个假设上的设计，任何一个塌了整份作废。此时暂停比推进便宜。

## G1｜需求门禁（spec → architect）

进入条件：`01-需求规格.md`、`02-验收标准.md` 已写。

| ID | 判断句（真/假） | 判定方式 | 证据位置 |
|---|---|---|---|
| G1.1 | 每条 `R#` 都能指回 `00` 的具体语句，或已标 `[假设]` | 取证 | `01` 需求表"来源"列 |
| G1.2 | 每个 `R#` 至少被 1 个 `AC#` 覆盖 | 机械 | `02` 覆盖列 |
| G1.3 | 每条 `AC#` 含「输入 → 动作 → 可观测输出」三段 | 取证 | `02` 每行三列齐全 |
| G1.4 | `02` 的判定条件中无不可测词（黑名单见 `contracts.md` §3） | 机械 grep | `02` 全文 |
| G1.5 | 不存在两条需求对同一输入给出互斥期望（无内部矛盾） | 取证 | `01` 冲突段必须写"无"或列出 |
| G1.6 | `01` 有"不做什么"且 ≥2 条 | 机械 | `01` 范围边界段 |
| G1.7 | 两份文件字数在限内（1200 / 900） | 机械 | `check_run.py` |
| G1.8 | 每条 `R#` 的来源能指向 `SC/OP`、`RULE-`、`EV-` 或 `[假设A#]` 之一（I11） | 机械 | `01` 来源列 |

**全 `是` → 放行到 architect，且 `02` 冻结。**

**G1.8 为什么单列**：G1.1 只要求"能指回 `00` 或标假设"。
但用户随口一句"要个支架"指回 `00` 是成立的，而它并不是一个有效需求来源。
G1.8 要求的是**工程来源**：要么从场景推出来（SC/OP），要么有标准依据（RULE/EV），要么明说是假设。
三者都指不上的 R，是拍脑袋。

**任一 `否` → 退回 spec**，带三样东西回去：
1. 失败检查项的 ID 与原文判断句；
2. 对应的 `R#`/`AC#` 编号（不是"整体重写"）；
3. 一个具体反例（"AC3 写的是'结果正确'，用 t2.md 跑无法判定真假"）。

不许退回到 lead 让它"帮忙改"，lead 不得代笔（C1）。

## G2｜方案门禁（architect → builder）

进入条件：`03-架构方案.md`、`04-实施路径.md` 已写，且 `02` 未被修改。

| ID | 判断句 | 判定方式 | 证据位置 |
|---|---|---|---|
| G2.1 | 关键决策每条都有「放弃项 / 理由 / 代价」三段，≥2 条 | 机械 + 取证 | `03` 取舍段，数 `｜` 分隔 |
| G2.2 | 失败模式 ≥2 条，每条含「触发 / 表现 / 兜底」 | 机械 | `03` 失败模式表 3 列非空 |
| G2.3 | 每个 `AC#` 有验证路径（命令或可执行步骤） | 机械比对 | `03` AC→验证映射覆盖全部 AC |
| G2.4 | 每条外部依赖写明版本、可用性、替代方案 | 取证 | `03` 依赖段 |
| G2.5 | 方案中无 `01` 范围边界之外的需求（无 scope creep） | 取证 | 逐条比对 `01` 边界 + `03` 组件 |
| G2.6 | `02` 的判据与 G1 通过时逐字一致（未迁就架构被改） | 机械 diff | `git diff` 中 `02` 无改动 |
| G2.7 | `04` 每步有产出路径与回退点，依赖无环 | 机械 | `04` 表格 5 列非空 |

| G2.9b | 规则包内 `R3` 规则的 `severity_if_fail` 只能是 advise（社区 checklist 不得拒收） | 机械 | run 与 skill 的 `rulepacks/*.yaml` |

**G2.9 的具体要求**：版本号不许写 `latest`；引用的 `RULE-` 必须在包文件里真实存在（防空引用）；
`level: R3` 的规则不得出现在 pass/fail 判据位置。给不出 `RULE-` 的参数，降级进 `00d` 假设表，不许写"经验值"。

**任一 `否` → 退回 architect**（G2.6 失败则退回 spec 并记 `07` 裁决）。带回：失败项 + 具体缺失字段（"取舍 2 缺'代价'"），不许说"方案再想想"。

## G3｜交付门禁（reviewer → 用户）

进入条件：`05-实现/` 可运行，`06-盲审报告.md` 已写。

| ID | 判断句 | 判定方式 | 证据位置 |
|---|---|---|---|
| G3.1 | `06` 的 `REVIEW_MODE` 为 `blinded`（`degraded`/`unblinded` 一律判否，除非 07 有用户显式接受该风险的裁决） | 机械 | `06` 头部 + `07` 裁决表 |
| G3.2 | `06` 结论为 `PASS`，或结论 `FAIL` 但所有 P0/P1 已在新一轮闭环 | 机械 | `06` 结论 + 问题清单 |
| G3.3 | 未闭环 P0 = 0 且未闭环 P1 = 0 | 机械 | `06` 问题清单级别列 |
| G3.4 | 每条 `AC#` 有通过证据（命令+输出 或 测试名+结果） | 机械 | `06` AC 证据表行数 = AC 总数 |
| G3.5 | 变更已提交（`git log` 有对应 commit，工作区干净或已登记） | 机械 | `git status` / `git log -1` |
| G3.6 | 遗留 P2/P3 已登记 `07`，含触发条件 | 取证 | `07` 最后一条 |
| G3.7 | `06` 不是无效审查（P0/P1/P2 全 0 时必须有"3 个攻击点 + 实际结果"） | 取证 | `06` 攻击段 |
| G3.8 | `08-追溯矩阵.md` 五类孤儿全为 0，L0–L7 八层均有落点（有孤儿即判否；带 `D#` 只改交付口径，不改门禁） | 机械 | `08` §1/§2/§3（见 `e2e-spine.md`） |
| G3.8b | 矩阵逐条列举 `01` 全部 R 与 `02` 全部 AC（孤儿填 0 但矩阵缺行 = 自述代替扫描） | 机械 | `08` §1 对照 `01`/`02` |
| G3.9 | 无绕过痕迹：`07` 无 `VOID` 未处置记录；同一 `file:line` 未超 3 轮；判级与 R 数量不自相矛盾（B7） | 机械 | `07` 全文 + `01` |

**全 `是` → 交付**，向用户输出"能交付/不能交付 + 证据摘要 + 遗留清单"。

**有未确认假设时的交付口径**：结论只能是 `PASS-WITH-ASSUMPTIONS`，
必须附假设清单与各自返工点。**不许给无条件 `PASS`**（见 `scenario.md` §输入缺口）。

**G3.9 判 B7 的条件**：`07` 判级为 `S`，但同时满足任一 —— `R#` > 6 / 涉及新认证或新供应链 /
跨 3 个以上模块。此时强制升级为 M 或 L 并补流程，不是"下次注意"。

**任一 `否` → 退回 builder**（G3.1/G3.7 失败则退回 reviewer 重审）。带回：未闭环问题 ID 列表 + 每条复现命令。

## 迭代上限与升级（C8）

1. 同一问题（同一 `R#`/`AC#`/同一 `file:line`）最多修 **3 轮**。
2. 第 3 轮仍不过 → **升级 lead 裁决**，写 `07`：谁主张、主张什么、反方理由、裁决、代价、待复核条件。
3. 裁决只有三种结果：`修需求`（回 G1）/`修实现`（回 builder）/`带缺陷交付`（必须写代价与用户可见影响）。
4. 不许出现第 4 轮；不许"再试一次"；不许静默把问题从 P1 降为 P2 来放行（降级本身就是裁决，必须入 `07`）。

## 门禁判定记录

每道门禁的判定结果必须落在 `07` 一行：`G1 通过 2026-11-22 / 检查 7 项 / 全真`。
不许只在对话里说"门禁通过了"。

`tests/test_attacks.py` 把 10 种"假装做完了"注入干净基线，逐个验证必被抓：

| 注入 | 预期门禁 |
|---|---|
| B1 自我豁免（lead 自批"本领域不适用"） | G2.9 + G3.9 |
| B3 静默降级（汇总 P1=0，清单混一行 P1） | G3.3 |
| B5 污染盲审（正文引用 03 的取舍理由） | G3.1b |
| R3 越权（社区 checklist 写 reject） | G2.9b |
| 伪造追溯矩阵（孤儿填 0，矩阵删行） | G3.8b |
| 空实现（函数体只有 pass） | I.1 |
| B7 拆小逃避（判 S 却 8 条需求） | G3.9 |
| B4 空产物（05 只剩 README） | I.0 |
| 条号造假（clause 待核却 verified） | G2.9c |
| 空壳直交（模板占位原样交付） | 任意 ≥5 NG |

改动 `check_run.py` 的判定逻辑后**必须跑**：`python tests/test_attacks.py`。
