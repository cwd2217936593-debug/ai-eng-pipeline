# 规模判级（sizing.md）

lead 的第一个动作永远是判级。判级的目的是**别用大炮打蚊子**——对小任务不友好的流程，在大任务上也活不下来（大家会绕过它）。

## 1. 判级表

| 维度 | S（单点） | M（单模块） | L（跨模块 / 新系统） |
|---|---|---|---|
| 影响文件 | 1 个 | 一个模块内 2-5 个 | 跨模块或全新工程 |
| 接口变更 | 无 | 模块内 | 对外接口/数据格式/持久化 |
| 需求条数 | 1-3 条，无歧义 | 4-8 条 | >8 条或有未知项 |
| 验收标准 | 一句话能说清 | 需 3-6 条 AC | 需分组 AC + 集成验证 |
| 回滚代价 | 删文件即可 | 一次 revert | 需迁移/兼容方案 |
| 是否开流水线 | **不开** | 开（轻） | 全开 |

## 2. 三条链路

**S｜单点直做**
`判定 → 直接实现 → 自检 → 交付`。不写 `01`-`04`，不跑盲审。lead 只需在 `07` 记一条判级。若实现中发现要动第二个模块 → 立即升级为 M，补 `01`/`02`。

**M｜单模块轻链**
`spec(01+02) → G1 → architect(03 精简 + 04) → G2 → builder(05) → reviewer 盲审(06) → G3`
精简含义：`03` 可省"依赖"外的扩展分析，但取舍与失败模式不可省。

**L｜跨模块全链**
`spec → G1 → architect → G2 → builder → reviewer → G3`，且 `03` 必含集成边界与迁移；`04` 必含分阶段可交付点；每阶段结束都要盲审一次。

## 3. 判级模糊时

- 拿不准 → **升一级**（S→M，M→L）。升级的代价是多写两份文件；降级的代价是漏掉集成问题。
- 例外：判为 S 但用户明确要"完整方案/正式交付" → 直接 M。
- 每次判级必须写：`级别 / 理由（对上面表格哪一行）/ 若判错往哪升`。

## 4. 降级（M→S）的唯一合法条件

同时满足：① 单文件 ② 无接口变更 ③ 验收可用一条命令判定 ④ lead 在 `07` 记录降级理由。
任一不满足即不许降级。

## 5. 领域差异（2.0 起三领域均支持）

判级前**必须先过 G0 定领域**。判级门槛随领域变化，具体数值见各领域包"槽位 8"：

| 领域 | S（单点） | M（单模块） | L（跨模块/新体系） | 本领域陷阱 |
|---|---|---|---|---|
| software | 单文件单函数、无接口变更、无新依赖 | 单模块、有内部接口、加 1 个依赖 | 多模块 / 跨系统 / 新框架 / 数据迁移 | 改一个"配置项"可能是全局开关 → 实为 L |
| hardware | 换阻容、改固件参数、不动板 | 单模块改动 + 一次改板 | 新板 / 新结构 / 新认证 / 新供应链 | 换一颗料可能换封装 → 改板 → L；加功能触发新认证 → L |
| hr | 改表单字段、调一个审批时限 | 单岗位职责 / 单流程节点 | 新考核体系 / 组织调整 / 涉薪酬编制 / 需职代会程序 | 改考核权重影响全员收入 → L；加考勤要求可能触碰工时 → 可能违法 → L |

**跨领域任务**（如"带 App 的硬件产品"、"绩效系统 + 配套开发"）：

1. 按**主交付物**定主领域（实物→hardware、代码→software、制度→hr）
2. 附属部分**单独分组 AC**（`AC-S1`、`AC-S2`…），不混在主 AC 里
3. 两套验证节奏写进 `04` 的**关键路径**：谁先谁后、谁阻塞谁、等待期能并行做什么

不得把两种节奏混在一条时间线上 —— 这是跨领域项目延期最常见的原因（代码写完了，样机还在等打样）。

## 6. 判级出错时

| 情况 | 处理 |
|---|---|
| 判 S 后想升 M | 允许，补 `01`/`02` 即可，`07` 记一句 |
| 判 M 后想升 L | 允许，`03` 补集成边界，`04` 加分阶段交付点 |
| 判 L 后想降 | 只在"发现实际范围远小于预估"时允许，且须 `07` 记理由 |
| **领域判错** | 回退 Stage 0，`01`–`03` 作废，`07` 记裁决 |
