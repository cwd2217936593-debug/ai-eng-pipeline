# 第一段：领域实例化（Stage 0）

> **这是整套流程的前置段，必须先于需求规格执行。**
> 它的唯一产出是 `00b-领域实例.md` —— 一份"本次任务要用哪套流水线"的施工图。
> 没有这份文件，不允许进入第二阶段。

---

## 为什么要有这两段

用户的原话：

> "在一开始用的这些 AI 比较多，在这些定完之后，我们才真正的开始去做，去生成一些真正干活的 AI。"

这个直觉是对的，而且它对应一个真实的工程教训：

**同一个流程套用到不同领域，失败的原因完全不一样。**

- 软件交付失败，多半是边界条件没覆盖（空输入、编码、并发）
- 硬件交付失败，多半是物理约束没满足（热、EMC、公差累积、来料波动）
- 人力资源方案失败，多半是合规与人心（劳动法、员工抵触、无法考核）

如果你拿"软件那套"去审一份人力资源方案，它会告诉你"缺少单元测试" —— 这是**正确的废话**，毫无用处。

所以必须有一个独立的阶段，先把"这次要用哪套标准"定下来，再开始干活。

**两段的分工**：

| 段 | 干什么 | 产出 | 谁参与 |
|---|---|---|---|
| **Stage 0** | 定领域、定角色、定验证方式、定攻击面 | `00b-领域实例.md` | 只有 lead + 用户（AI 用得少，但决策重） |
| **Stage 1+** | 按定好的施工图，逐环节产出与审查 | `01`–`07` | 全部角色（按 `00b` 实例化） |

Stage 0 是"元设计"，Stage 1+ 是"施工"。
**元设计错了，后面越努力越错。**

---

## Step 0.1 · 识别领域

先从用户表述里提取领域信号。**不要直接问"你是什么领域"** —— 用户往往在描述任务，不在描述领域。

### 关键词信号表

| 信号词 | 判定 |
|---|---|
| 代码、接口、部署、数据库、前端、后端、脚本、API、并发、日志 | `software` |
| 电路、原理图、PCB、固件、BOM、样机、EMC、散热、公差、元器件、模具 | `hardware` |
| 招聘、岗位、绩效、薪酬、培训、组织、编制、员工关系、劳动合同、制度 | `hr` |
| 制度 + 流程 + 审批 + 考核（无技术词） | 倾向 `hr` 或 `ops`（运营） |
| 同时出现两类信号 | 见下方"混合领域" |

### 判定规则

1. **单一信号 → 直接定**，不问。
2. **无信号 → 问一句**：*"这件事的交付物是什么？代码、实物、还是一份方案/制度？"* 只问这一句。
3. **两类信号各占一半 → 判为混合**，按主交付物定主领域，另一类作为附属包（见 Step 0.4）。
4. **判错了 → 允许改**，但必须回退到 Stage 0 重做 `00b`，并在 `07` 记一条裁决。不许边干边换。

### 用户明确指定时

用户如果说"这是硬件的"，直接采信，不要再从关键词反推。**用户的领域判断优先于你的推断。**

---

## Step 0.2 · 加载领域包

按判定结果读对应文件：

| 领域 | 文件 | 提供的核心内容 |
|---|---|---|
| `software` | `references/domains/software.md` | 验证=自动化测试；载体=代码；攻击面=边界/编码/并发 |
| `hardware` | `references/domains/hardware.md` | 验证=样机台架+认证；载体=BOM/图/固件；攻击面=热/EMC/公差/来料 |
| `hr` | `references/domains/hr.md` | 验证=试点+指标+回访；载体=制度/岗位/流程；攻击面=合规/可考核性/抵触 |
| `custom` | `references/domains/_template.md` | 用户自建领域，按模板填 7 个槽位 |

领域包**只提供变量**（见 `invariants.md` 末尾的五列），**不能覆盖任何不变量**。
如果某个领域包想改不变量 → 拒绝，改为在 `00b` 声明豁免并降级。

## Step 0.3 · 写 `00b-领域实例.md`

这是 Stage 0 的唯一产物。**必填字段，缺一项 G0 不过。**

| 字段 | 内容 | 不合格示例 |
|---|---|---|
| `domain` | 领域标识 | `"软件相关"`（不是标识，是形容词） |
| `判定依据` | 命中了哪些信号词 / 用户原话 | `"感觉是软件"` |
| `角色映射` | 5 个通用角色 → 本领域的实际角色名 + 职责偏移 | 缺 `reviewer` 一行 |
| `交付实体` | `05` 目录里到底放什么 | `"产出物"`（等于没说） |
| `验证方式` | AC 的判定手段是什么，谁执行，多久拿到结果 | `"测试一下"` |
| `攻击面` | reviewer 优先攻击的 5 类问题（本领域特有） | 照抄软件的五类 |
| `附加合规` | 本领域必须额外过的审批/法规（如 EMC 认证、劳动法审查） | 空着但领域是 `hr` |
| `豁免声明` | 若某条不变量确实无法满足，写明编号 + 理由 + 降级方式 | 没声明却绕过了 |
| `requires_core` | 依赖的不变量内核版本范围 | 留空 |

### 角色映射表格式（强制）

```
| 通用角色 | 本领域角色 | 职责偏移 | 额外要求 |
|---|---|---|---|
| lead | 项目负责人 | 无 | 无 |
| spec | 需求分析师 | 要出"可测试的需求"而非"功能描述" | 无 |
| architect | 系统架构师 | 无 | 需给出容差预算 |
| builder | 开发工程师 | 无 | 无 |
| reviewer | 代码审查员 | 无 | 必须会写测试 |
```

角色**可以增**（例如硬件加"EMC 评审"），**不能减**。5 个通用角色一个都不能少 —— 少一个就少一道校验。

### 合格示例（软件）

```
domain: software
判定依据: 用户原话含"命令行工具""转 CSV"，命中 代码/脚本/命令行 三类信号
角色映射: 见下表（5 个，无额外）
交付实体: 05-实现/ 下的可执行脚本 + 测试文件
验证方式: pytest 或直接命令行执行；判定看 stdout/退出码；秒级反馈
攻击面:
  1. 分隔/切分边界（行尾、空单元格、最后一个字段、转义未 flush）
  2. 空与不存在（空文件、空表格、文件不存在、参数缺失）
  3. 行尾与编码（CRLF、BOM、UTF-8 多字节截断、Windows 路径）
  4. 状态泄漏（多次调用间未重置的缓冲）
  5. "看起来通过"的测试（只查退出码不查内容）
附加合规: 无
requires_core: ">=2.0 <3.0"
```

### 不合格示例

```
domain: 软件
判定依据: 用户要做工具
角色映射: 架构师、开发、测试
交付实体: 工具
验证方式: 测试通过
攻击面: 各种边界情况
```

问题：`domain` 不是可识别的标识；判定依据没有原话；角色只有 3 个（缺 lead 和独立 reviewer）；交付实体没说是文件还是别的；验证方式无判定手段；攻击面无具体项。

## G0 · 领域门禁（新增，在 G1 之前）

全部满足才进入 Stage 1：

- [ ] `domain` 是可识别的标识（`software` / `hardware` / `hr` / `custom`）
- [ ] `判定依据` 里引用了用户原话或具体信号词
- [ ] `角色映射` 覆盖全部 5 个通用角色，且 reviewer 与 builder 不是同一角色
- [ ] `交付实体` 能在 `05` 目录里落地（说得清放什么文件）
- [ ] `验证方式` 说清了"谁、用什么手段、多久拿到结果"
- [ ] `攻击面` ≥5 条，且是本领域特有（不是照抄别的领域）
- [ ] `豁免声明` 与 `domain` 一致（`hr` 不应空着合规项）
- [ ] **用户已确认**（把 `00b` 摘要用三行讲给用户，得到"对"才继续）

**不过时怎么办**：退回 Stage 0 重写 `00b`。不许带着未确认的领域实例进入 Stage 1 —— 领域错了，后面全废。

## Step 0.4 · 混合领域怎么处理

用户的需求经常跨领域。例如"做一个带 App 的硬件产品"（hardware + software）、"设计绩效考核系统并配套开发"（hr + software）。

处理原则：**一个主领域，若干附属包**。

```
domain: hardware (primary)
attached:
  - software: 仅覆盖上位机 App 部分（验证方式用软件包）
```

规则：
1. 按**主交付物**定主领域（实物 → hardware；代码 → software；制度 → hr）
2. 附属包只提供"该部分的验证方式与攻击面"，**不改主流程**
3. 附属部分必须有自己的 AC 分组（`AC-S1`、`AC-S2`…），不能混在主 AC 里
4. 两套验证节奏要写进 `04-实施路径.md`：谁先谁后、谁阻塞谁

**最常见的事故**：硬件项目按软件节奏排期，导致"代码写完了，样机还在等打样"。这个必须在 Stage 0 就排清。

---

## Step 0.5 · 领域判错的代价

判错领域有两种，代价完全不同：

| 情况 | 表现 | 处理 |
|---|---|---|
| **判错但没开工** | Stage 0 内发现 | 改 `00b`，重过 G0，无成本 |
| **判错且已开工** | 执行到 `03` 才发现验证方式不对 | **必须回退**，`01`–`03` 作废重写，`07` 记裁决 |

所以 G0 的"用户已确认"那一条不能省。**这是整套流程里最便宜的一次确认。**

---

## 给不同平台的操作差异

| 平台 | Stage 0 怎么执行 |
|---|---|
| 有子代理能力（WorkBuddy / Claude Code） | lead 在本对话做，产物落盘 |
| 单轮对话（ChatGPT 网页） | 先只做 Stage 0，输出 `00b` 全文，让用户确认后再开新对话做 Stage 1 |
| 纯文本模型 | 把 `00b` 当作"施工图"贴在每条后续消息开头 |

Stage 0 天然适合"单独一次对话完成"，因为它只需要少量推理，不需要大量产出。这一点对跨平台特别友好。
