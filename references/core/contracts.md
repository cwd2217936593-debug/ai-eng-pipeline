# 产物契约（contracts.md）

本文件是整条流水线唯一的"接口定义"。写任何产物之前先读本文件；写任何产物之后必须能对上本文件。

**核心原则：产物优先于角色。** 决定质量的是上游交给下游的信息结构，不是人设。角色卡只是"我读哪几个文件、写哪个文件"的执行器。

---

## 0. 通用规则（对所有产物生效）

1. **编号稳定**：文件名与编号一旦发布，永不重排、永不复用。新增产物用 08、09 追加，不插入。
2. **落盘优先**：任何结论若只存在于对话里，视为不存在。下游只读文件，不读上游推理过程（C3：串行 5 环，每环 10% 偏差，终点偏差约 41%）。
3. **不许概括原文**：`00-原文.md` 只追加不改写。任何"用户其实是想要……"的解释必须写进 `01` 的假设段，并标 `[假设]`。
4. **字数算法**：汉字按字计，连续拉丁字母/数字按 1 词计（`count_units`）。超限 = 该产物不合格，门禁直接不过，不需要讨论内容好坏。
5. **路径精确**：所有产物路径相对 `run-YYYYMMDD-NN/`。`05-实现/` 内部路径自由，但必须在 `04` 中登记。
6. **一个事实只写一处**：验收判据只写在 `02`；`03`/`04`/`06` 只能引用 `AC-x`，不能复述或改写判据。复述即视为篡改。

### 字数上限总表（硬性，超一字即不合格）

| 编号 | 文件 | 上限（单位） |
|---|---|---|
| 00 | `00-原文.md` | 5000（超出拆 `00-1`/`00-2`，原文仍不改写） |
| 00b | `00b-领域实例.md` | 600 |
| 00c | `00c-领域取证.md` | 1500（仅 `domain: custom`） |
| 00d | `00d-场景工况.md` | 900 |
| 01 | `01-需求规格.md` | 1200 |
| 02 | `02-验收标准.md` | 900 |
| 03 | `03-架构方案.md` | 1500 |
| 04 | `04-实施路径.md` | 800 |
| 05 | `05-实现/` | 无总量上限，单文件 ≤ 300 行 |

## 0c. `00c-领域取证.md` — 陌生领域证据台账（Stage 0.5 产物）

> **2.1 新增。仅 `domain: custom` 时存在。** 它回答一个问题：`02` 里的判据凭什么算判据。

| 项 | 内容 |
|---|---|
| 文件名与编号 | `00c-领域取证.md` |
| 写者 | lead（可委派取证子角色；但台账由 lead 汇总，责任不转移） |
| 读者 | spec（写 AC 时引 `[EV-xx]`）、architect（量化参数的依据）、reviewer（核对判据可溯源性） |
| **不读者** | 无 |
| 必填字段 | 证据台账（ID/等级/来源/日期/摘录/可用于）/ 未取证清单 / 架构适配假设 / 取证能力声明 |
| 字数上限 | 1500 |
| 进下一阶段门槛 | G0.9 全真。核心一条：**每条将写入 `02` 的判据都能追到 E0 或 E1** |

**三条硬约束**

1. **未取证清单不许为空。** 一份诚实的陌生领域取证必然有一堆没核实的推测；清单空了不是"查清了"，是"没查"。
2. **E3 不许进 `02`，也不许进 `03` 的量化参数**（公差、载荷、时限、比例、阈值）。E3 的唯一合法用途是生成待确认问题。
3. **取证能力声明必须与实际工具一致。** 无联网无知识库时只能到 E3，此时应停下向用户索取材料，而不是继续往下写。

**合格示例**

```
| EV-01 | E1 | GB 50011-2010《建筑抗震设计规范》第 8.1.3 条 | 2026-11-22 | 钢结构房屋应根据设防分类、烈度和房屋高度采用不同的抗震等级 | AC3 |
```

**不合格示例**

```
| EV-01 | E1 | 国家建筑标准 | 2026-11-22 | 应符合国家现行标准 | AC3 |
```

问题：没有标准号、没有条号、没有原文摘录 —— 这三样缺任何一样，这条证据就无法核验，等于没有。

## 0d. `00d-场景工况.md` — 场景与工况（Stage 0 产物）

> **3.0 新增。所有领域都要有，不只 custom。** 它回答一个问题：这个东西要在什么条件下活着。
> 没有它，需求就是从用户那句话直接猜出来的（违反 I11）。

| 项 | 内容 |
|---|---|
| 文件名与编号 | `00d-场景工况.md` |
| 写者 | spec 起草，lead 汇总确认（场景是需求的上游，不该由写需求的人独家决定） |
| 读者 | spec（推需求）、architect（定参数）、reviewer（判"AC 是否覆盖场景"） |
| 必填字段 | 一句话场景 / SC1–SC8 八槽位 / OP 工况参数表 / DC 设计约束表 / 假设登记 / 场景标签 |
| 字数上限 | 900 |
| 进下一阶段门槛 | G0.10 全真 |

**三级推导不许跳**

```
SC（场景槽位，定性）→ OP（工况参数，带数值单位）→ DC（设计约束，带 RULE-/EV- 出处）→ DF（设计特征）
```

**四条硬约束**

1. **槽位不许写"待定/视情况"**。给不出就进假设表，给具体值 + 若错代价 + 方向。
2. **OP 必须带单位和数值**。"低温"不是参数，"-40℃"才是。
3. **DC 必须挂 `RULE-` 或 `EV-`**。挂不上的说明它还是"经验"，该进假设表。
4. **假设有上限**：S=2 / M=5 / L=8。超限不是"记录得好"，是需求没聊清楚。

**合格示例（DC 一条）**

```
| DC1 | -40℃ 下材料冲击吸收能量满足标准规定值 | RULE-FST-001 | 选材：A4-70 或低温钢 | 低温冲击试验报告 |
```

**不合格示例**

```
| DC1 | 用不锈钢，耐低温 | 经验 | 选材 | 看情况 |
```

问题：没有具体判据值（多少焦耳）、来源是"经验"（等于没有）、验证方法是"看情况"（不可判定）。

## 6. `05-实现/` — 交付实体（形态随领域变化）

| 项 | 内容 |
|---|---|
| 文件名与编号 | 目录 `05-实现/` |
| 写者 | builder |
| 读者 | reviewer、lead |
| **不读者** | spec、architect（实体写完不再回头改契约；要改走裁决） |
| 必填字段 | 每个 `AC-x` 有对应的验证手段；`05-实现/README.md` 写明使用方式与 AC→验证映射 |
| 字数上限 | 无总量上限；单文件 ≤300 行 / 单文档 ≤2000 字（超出拆文件） |
| 进下一阶段门槛 | 能按 README 跑通或执行；AC 映射齐全；无占位与假实现 |

**各领域交付实体对照**（完整定义见各领域包槽位 1）：

| 领域 | `05` 里放什么 | 什么算"假交付" |
|---|---|---|
| software | 代码 + 测试 + 运行说明 | `TODO` / 空实现 / 硬编码期望值让测试通过 |
| hardware | 原理图 / PCB / BOM / 固件 / 结构图 / 台架实测记录 | 只有框图无参数 / BOM 缺封装耐压 / "预计满足"当实测 |
| hr | 制度正文 / 岗位说明 / 流程 / 指标定义表 / 表单模板 | 有指标无数据源 / 有流程无决策人与时限 / 通篇"加强、提升、优化" |

**通用的"假实现"禁令**：占位符、把异常捕获后吞掉、把期望值直接写死、用"后续完善"代替内容。
不论哪个领域，"看起来完成了但其实没有"都算 P0。

**禁止的"假实现"**：`TODO`、`pass  # 待实现`、`return True  # 简化处理`、把异常捕获后 `pass` 吞掉、硬编码测试期望值以通过测试。

**合格示例**（可运行、可判定）

```python
def split_row(line: str) -> list[str]:
    cells, buf, esc = [], [], False
    for ch in line.strip().strip("|"):
        if esc:
            buf.append(ch); esc = False
        elif ch == "\\":
            esc = True
        elif ch == "|":
            cells.append("".join(buf).strip()); buf = []
        else:
            buf.append(ch)
    cells.append("".join(buf).strip())
    return cells
```

**不合格示例**

```python
def split_row(line):
    # TODO: 处理转义
    return line.split("|")
```
（不合格理由：转义需求 R2 直接丢失，但测试若不覆盖这条就会"通过"。）

| 必填字段 | `REVIEW_MODE`、审查者读过的文件清单、结论 PASS/FAIL、≥3 个攻击点、问题清单（带 P0-P3）、AC 证据核对表、未能验证的部分 |
| 字数上限 | 1000 |
| 进下一阶段门槛 | `REVIEW_MODE: blinded`（或已登记的降级）；P0/P1 全为 0；且不满足"无效审查"判据 |

**严重级别定义（不得自行发明第 5 级）**

- **P0 阻断**：数据错误、崩溃、AC 未实现、静默错转。必须修，不许放行。
- **P1 严重**：错误处理缺失、边界未覆盖、AC 证据缺失。必须修。
- **P2 一般**：与 AC 无关的可用性/可维护性问题。可延后，但需进 `07` 登记。
- **P3 建议**：风格、命名、注释。仅登记。

**无效审查判据（防止"一路通过"）**：若 P0、P1、P2 全为 0，则报告必须包含"我尝试弄坏它的 3 个具体手段 + 每个手段的实际执行结果"。缺此段 = 本次审查作废，`REVIEW_MODE` 记 `invalid`，G3 不过。

**多轮审查不覆盖**：第 1 轮存为 `06-盲审报告-r1.md`，第 2 轮存为 `06-盲审报告-r2.md`，只有**最终轮**写成 `06-盲审报告.md`。`check_run.py` 只读 `06-盲审报告.md`，所以最后一轮必须改名回来。保留历史轮次的目的是：证明审查真的拦下过东西，而不是每轮都通过。

**合格示例**

```
| ID | 级别 | 位置 | 现象 | 复现 | 修法 |
|---|---|---|---|---|---|
| I1 | P0 | 05-实现/mdtable2csv.py:14 | 行尾 `\|` 被当作列分隔，AC2 失败 | `printf '| a\\|b |\n' > t.md && python mdtable2csv.py t.md` 输出 4 列 | 转义状态在行尾未 flush，补 `if esc: buf.append("\\")` |
| I2 | P1 | 05-实现/mdtable2csv.py:3 | 无参数时抛 IndexError 栈，AC3 的退出码契约未覆盖 argv 为空 | `python mdtable2csv.py` | 参数校验前置，退出码 2 |
```

**不合格示例**

```
整体实现质量良好，逻辑清晰，建议进一步优化错误处理和代码结构，可以考虑增加更多测试。
结论：通过。
```
（不合格理由：无位置、无级别、无复现、不可执行；"建议进一步优化"是软话，等于什么都没说。）

## 9. 追溯规则（机械可查）

1. `01` 中每个 `R#` 必须在 `00` 有可定位来源，或在 `01` 假设段标 `[假设]`；
   **v3.0 起**还须指向 `SC/OP`、`RULE-`、`EV-` 或 `[假设A#]`（G1.8）。
2. `02` 中每个 `AC#` 必须引用存在的 `R#`；每个 `R#` 至少被一个 `AC#` 覆盖。
3. `03` 的 AC→验证路径映射必须覆盖 `02` 全部 `AC#`。
4. `05` 的 AC→测试映射必须覆盖 `02` 全部 `AC#`。
5. `06` 的证据核对表必须逐条列出 `02` 全部 `AC#`，缺一条即 P1。
6. `08` 的五类孤儿统计必须全为 0，L0–L7 八层必须有落点。
7. `scripts/check_run.py` 会机械校验 1-2、6 与字数/结构；3-5 靠 reviewer 人工对照。
