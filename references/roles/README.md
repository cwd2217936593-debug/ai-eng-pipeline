# 角色卡（roles/）

| 通用角色 | 文件 | 只做 |
|---|---|---|
| lead | `lead.md` | 判级、选链、裁决 |
| spec | `spec.md` | 需求清单 + 验收标准 |
| architect | `architect.md` | 方案（取舍/失败模式）+ 实施路径 |
| builder | `builder.md` | 交付实体 |
| reviewer | `reviewer.md` | 独立盲审 |

## 读角色卡之前，先读 `00b-领域实例.md`

角色卡写的是**动作**，不是**领域知识**。

例如 `builder.md` 说"产出可运行的东西"：
- software → 代码 + 测试
- hardware → 图纸 + BOM + 固件 + 实测记录
- hr → 制度正文 + 表单 + 指标定义表

**领域知识不在角色卡里，在 `domains/<x>.md` 里。** 角色卡里的"代码""测试"等字样，一律按 `00b` 的角色映射替换为本领域的对应物。

## 三条铁律

1. **5 个角色一个都不能少。** 少一个就少一道交叉校验。可以**加**（如硬件加 EMC 评审、HR 加法务审查），不能**减**。
2. **reviewer 不得是 builder。** 同一个上下文里自己审自己，审查会永远通过，而且你不会发现（见 `core/invariants.md` I4）。
3. **lead 不写实质内容。** 只判级、选链、裁决。一旦它开始写需求或做技术选型，它就是瓶颈和幻觉源（I8）。

## 角色卡为什么这么短

每份 ≤800 字，且不写"你是一位有 20 年经验的资深专家"。

原因：**人设对输出质量的影响极小，真正的杠杆在交接物结构。**
同一个模型，给它一段混乱口述，它出垃圾；给它一份带约束和验收标准的结构化规格，它出精品。

所以力气应该花在 `core/contracts.md`（产物契约），不是花在把人设写得更像专家。

## 角色之间怎么通信

**只通过文件。** 不通过对话，不通过"我记得刚才说过"。

每个角色卡第 1 节都写死了"我读哪些文件"、第 2 节"我写哪个文件"。这是唯一合法的接口。

串行 5 环，每环 10% 理解偏差 → 终点偏差约 41%。文件是锚点，对话是流沙。
