# 盲审协议（blind-review.md）

## 1. 为什么必须隔离（C5）

同一上下文里做审查，审查者已经读过生产者的推理（"这里我故意简化，因为……"），于是会**替作者找理由**。这种审查每次都会说"通过"，而且没有人会发现它失效——因为它的错误方向永远是放行。

所以：**reviewer 必须是全新上下文的子代理，只能用文件与它通信。**

## 2. 三件套（只给这三个路径，多一个都不给）

1. 产物：`<RUN>/05-实现/`（或需要审的 `01`+`02`）
2. 判据：`<RUN>/02-验收标准.md`
3. 原始需求：`<RUN>/00-原文.md`

**不给**：`01`、`03`、`04`、对话历史、你的判断、你"已知的三个 bug"。

## 3. 主路径：起 Agent 子代理

用 `Agent` 工具（`subagent_type: general-purpose`，若是 Task 工具同理），prompt 必须**完全自包含**——子代理看不到本对话。模板如下，`{{}}` 替换为绝对路径：

```
你是独立审查者。你与新代码的作者没有任何上下文共享，这是刻意设计。

【硬约束】
1. 你只能读这三个路径：{{PRODUCT}}、{{AC_FILE}}、{{ORIGINAL}}
2. 不得读取其他任何文件，不得询问调用方任何问题，不得推测未提供的信息。
3. 你是只读的：不得修改、创建、删除任何文件（除你自己的报告外）。
4. 缺信息就写"无法验证"，不许猜。

【你的工作】
A. 报告开头写 REVIEW_MODE: blinded，并逐条列出你实际读过的文件绝对路径。
B. 先不看实现细节，写下 3 个"我会怎么弄坏它"的具体手段（例：行尾转义、空输入、CRLF、超长单元格、
   表头列数不一致、文件不存在、参数为空）。逐个**实际执行**并在报告里贴真实输出。
C. 逐条核对 {{AC_FILE}} 中每个 AC#：给出证据（命令 + 实际输出摘要，或测试名 + 结果），
   结果只能是 通过 / 未通过 / 无法验证。缺任何一条 AC 即记 P1。
D. 每个问题给 P0/P1/P2/P3（P0 数据错误或崩溃或 AC 未实现；P1 错误处理/边界/证据缺失；
   P2 一般；P3 建议），必须带 file:line 与复现命令。
E. 结论：PASS 仅当 P0=P1=0 且每条 AC 有通过证据，否则 FAIL。

【禁止】
- 禁止"建议进一步优化""整体质量良好""可以考虑增强健壮性"这类无法执行的评价。
- 禁止写"可能存在风险"而不复现。要么给命令和输出，要么归入"未能验证"。
- 禁止因为作者可能很努力而降低级别。
- 禁止只输出"通过"而不给攻击过程；P0/P1/P2 全为 0 时，必须给出 3 个攻击点的实际执行结果。

【输出】只输出 06-盲审报告.md 的完整 Markdown 内容（≤1000 字），按
`REVIEW_MODE / 读过的文件 / 攻击点 / 问题清单表 / AC 证据表 / 未能验证` 六段组织。
```

收到返回后，由 lead 把内容**原样**写入 `06-盲审报告.md`，不得润色、不得删减级别、不得"整理一下语气"。润色即篡改。

## 4. 隔离有效性校验

报告到手后，lead 检查三件事，任一不满足则本次审查作废（`REVIEW_MODE: invalid`，G3 不过）：

1. 文件清单里只有被授权的三个路径；
2. 报告里没有出现未提供文件的内容（如引用"架构文档第 4 节"→ 污染）；
3. 结论与问题级别自洽（有 P0 却 PASS → 无效）。

## 5. 降级阶梯（环境没有子代理工具时）

按顺序尝试，**不许跳级，不许假装**：

1. **`blinded`（首选）**：`Agent` 子代理，如上。
2. **`degraded`（次选）**：另起一个独立进程做审查（例如通过 CLI 以单次 prompt 方式启动），同样只传三个路径。报告里记 `REVIEW_MODE: degraded`，并在 `07` 记一条裁决说明原因。
3. **`unblinded`（最后手段）**：当前上下文自审。必须在 `06` 记 `REVIEW_MODE: unblinded`，且**必须**：
   - 把"三个攻击点"的实际命令与真实输出贴全（自审的可信度只来自可复现证据）；
   - 在 `07` 记一条裁决：`审查未隔离，可信度下降，代价=可能替作者圆场`；
   - G3.1 判 `否`，直到用户在 `07` 显式接受该风险。

**绝对禁止**：不声明模式就交付、把 `unblinded` 写成 `blinded`。

## 6. 审查该抓什么（给 reviewer 的隐性知识，写在协议里而非角色卡）

软件任务里 80% 的 P0 来自这五类，优先攻击：

1. **分手/切分边界**：行尾、空单元格、最后一个字段、转义未 flush。
2. **空与不存在**：空文件、空表格、文件不存在、参数缺失。
3. **行尾与编码**：CRLF、BOM、UTF-8 多字节截断、Windows 路径。
4. **状态泄漏**：多次调用之间未重置的全局/缓冲。
5. **"看起来通过"的测试**：断言只查退出码不查内容、硬编码期望值、测试里吞异常。

## 7. 谁不能做 reviewer

- 写过本轮 `05` 的同一个上下文（必须换代理）；
- 读过 `03` 的上下文（已被架构理由污染）；
- lead 自己（lead 只判门禁，不产出审查结论）。
