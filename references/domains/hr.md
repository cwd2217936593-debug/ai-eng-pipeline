# 领域包 · 人力资源 / 组织制度（hr）

> 本包也适用于：流程制度、运营规范、内部管理办法 —— 凡"交付物是文本 + 行为改变"的领域。

## 槽位 1 · 交付实体

```
05-实现/ 放：制度正文、岗位说明书、流程图、表单模板、指标定义表、培训材料、FAQ
由谁使用：HRBP（执行）、部门负责人（落地）、员工（遵守）、法务（审查）
怎么确认真实：能直接下发执行，且每条规定都指向一个可采集的数据或可观察的行为
```

**禁止的假交付**：
- 「加强」「提升」「优化」开头但没说什么动作的条款
- 有指标名但没有数据源的（"客户满意度"——谁采、怎么采、多久一次）
- 有流程但没有决策人/时限的（"相关部门审核"——哪个部门、几天）

## 槽位 2 · 验证方式

```
判定手段：小范围试点 → 采集指标 → 员工回访 → 修订 → 推广
执行者：HRBP 组织试点，部门负责人执行，员工被回访
反馈周期：1 个考核周期（月/季），**不能更快** —— 这是本领域最硬的约束
做一次验证的成本：1 个部门 × 1 个周期的人力 + 沟通成本
外部机构：无（除非涉及劳动争议仲裁/个保合规评估）
```

**核心原则**：HR 领域的验证周期以"月"计，所以**试错代价极高**。这意味着两件事：

1. 必须先在纸上把"可考核性"想清楚，不能"发下去再看"
2. 试点范围要小到"错了也只影响一个组"

## 槽位 3 · 方案载体

`03-架构方案.md` 里的"架构"指：

```
1. 组织结构（谁向谁汇报、谁对什么负责）
2. 岗位与职责（每个岗位 3–5 条核心职责，不写"其他领导交办"）
3. 流程节点（谁发起→谁审→谁批→谁归档，每步有时限）
4. 决策权分配（什么事谁拍板，金额/人数/例外权限）
5. 指标树（公司级→部门级→岗位级，每级有数据源）
6. 例外与申诉通道（不合规情况找谁、多久答复）
```

**必须量化的**：

| 项 | 必须给 |
|---|---|
| 流程时限 | 每个审批节点的最长处理时间 |
| 指标 | 每个指标的计算公式 + 数据源 + 采集频率 |
| 覆盖 | 适用人数/岗位数，例外人数 |
| 成本 | 每人每月的填报/审批时间估算 |

## 槽位 4 · 攻击面

reviewer 优先攻击这七类：

| # | 攻击面 | 具体打点 |
|---|---|---|
| 1 | **合法性** | 单方变更劳动合同内容、解除程序、加班与调休、竞业限制补偿、试用期约定 |
| 2 | **程序合规** | 涉及员工切身利益的制度是否经职代会/全体讨论、是否公示告知、是否有签收记录 |
| 3 | **可考核性** | 指标有无数据源、口径是否唯一、是否可被操纵（凑数/刷量） |
| 4 | **执行成本** | 表单数量、审批层级、是否挤压一线作业时间 |
| 5 | **员工抵触** | 是否增加了工作量却不给对应激励；是否削弱某岗位权力；是否有"秋后算账"感 |
| 6 | **例外情形** | 特殊岗位（外派/倒班/孕产/工伤）、老员工过渡、跨地域差异 |
| 7 | **数据与隐私** | 个人信息采集范围是否必要、是否超范围、留存期限、谁能查 |

附加：与现有制度冲突（新旧并行）、跨部门职责空白（都以为对方管）、指标之间的反向激励（为达标损害另一目标）。

## 槽位 5 · 角色映射

| 通用角色 | 本领域角色 | 职责偏移 | 额外要求 |
|---|---|---|---|
| lead | 项目负责人（HRD/HRBP 主管） | 要管沟通与试点排期 | 懂组织政治 |
| spec | 制度需求分析师 | 要出"可考核的行为要求"而非"管理理念" | 能把口号翻译成动作 |
| architect | 组织与流程设计 | 见槽位 3 六项 | 必须给指标的数据源 |
| builder | 制度起草人 | 出制度/表单/流程/培训材料 | 每条要求可执行 |
| reviewer | 合规与落地评审 | 见槽位 4 | **必须懂劳动法**；最好有员工代表视角 |
| （建议加） | 法务审查 | 专项合法性审查 | 挂在 G2 之后、G3 之前 |

**reviewer 的双重身份**：既要能判断"合法吗"，也要能判断"落得下去吗"。只懂法不懂业务的审查，会产出一份合法但没人执行的制度。

## 槽位 6 · 附加合规

```
必须过的关卡：
  劳动法 / 劳动合同法（变更、解除、工时、假期）
  个人信息保护法（员工信息采集的最小必要）
  工会法 / 职代会程序（涉及切身利益的制度）
  同工同酬、反就业歧视
  行业特殊规定（国企/事业单位的报批流程）
谁签：法务 + 工会（如需）+ 分管领导
挂在哪个门禁上：G2（方案定案时确认路径合法）与 G3（有法务签署意见才交付）
```

**注意**：HR 领域的"合规"不是形式审查。一条违法条款会让整份制度失效，且可能引发集体争议。所以法务必须在 G2 就介入，不能等到 G3 盖章。

## 槽位 7 · 判定用语

```
合格：新考勤制度在 A 部门试点 4 周，员工日填报耗时中位数 3 分钟（问卷 n=28），
      异常数据 100% 可从现有打卡系统导出，无需人工补录
合格：制度第 5.2 条经 2026 年第二次职代会审议通过（附纪要编号），公示 7 日无异议
不合格：提升员工满意度，增强组织活力
不合格：流程更加顺畅，管理更加规范
本领域禁用语：提升、加强、优化、赋能、闭环、抓手、颗粒度
```

## 槽位 8 · 判级门槛

```
S：改一份表单字段、调整一个审批时限
M：一个岗位的职责调整 / 一条流程的节点变更
L：新考核体系 / 组织架构调整 / 涉及薪酬或编制的变更 / 需要职代会程序
典型陷阱：改一个"考核权重"看起来是 S，但它改变了所有人的收入 → 实际是 L
         加一条"考勤要求"看起来是 M，但涉及工时制度 → 可能违法 → 实际是 L
```

## 本领域的特殊提醒

**HR 是三个领域里"验证最弱"的一个。**

- 软件能秒级跑测试
- 硬件能上台架测
- HR 只能"发下去看几个月"

这个特性导致一个系统性风险：**因为无法快速验证，所以倾向于把制度写得"看起来周全"** —— 条款越多、措辞越正式，越有安全感。但条款越多，执行成本越高，最后没人执行，制度变成文件柜里的装饰。

所以本领域的审查重点，不是"条款够不够全"，而是：

> **每一条，能不能回答"怎么知道它被执行了"？**

回答不了的条款，要么删掉，要么补上数据源。这是 HR 领域的 I3（可验证性前置）的具体形态。
