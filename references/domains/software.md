# 领域包 · 软件（software）

## 槽位 1 · 交付实体

```
05-实现/ 放：可执行代码 + 可执行测试 + 一份 README（运行方式 + AC→测试映射）
由谁使用：builder 自己跑、reviewer 独立跑、用户最终运行
怎么确认真实：能在干净环境里跑起来并复现 AC 的结果，不是"伪代码"或"设计片段"
```

**禁止的假实现**：`TODO`、`pass  # 待实现`、`return True  # 简化处理`、捕获异常后 `pass` 吞掉、硬编码期望值让测试通过。

## 槽位 2 · 验证方式

```
判定手段：自动化测试（pytest/unittest）优先；无测试框架时用"命令 + 期望输出"表格
执行者：builder 自测 → reviewer 独立复跑（必须自己敲命令，不许只看 builder 的截图/日志）
反馈周期：秒级（单测）到分钟级（集成）
做一次验证的成本：近乎零 —— 这是软件最大的优势，也是它最容易偷懒的地方
外部机构：通常无；涉及等保/渗透测试时另算（1–4 周）
```

**关键**：反馈周期短 → 更容易"看起来通过"。所以本领域的审查重心不在"有没有跑"，而在"**断言是否有意义**"。

## 槽位 3 · 方案载体

`03-架构方案.md` 里的"架构"指：

```
1. 模块划分（有哪些文件/类，各自职责一句话）
2. 接口定义（函数签名、输入输出、错误码）
3. 数据流（数据从哪来到哪去，谁持有状态）
4. 依赖方向（谁依赖谁，是否成环）
5. 失败处理策略（异常/降级/重试）
```

**必须量化的**：错误码表（每个非正常路径一个码）、单文件行数上限、外部依赖清单（含版本）。

## 槽位 4 · 攻击面

reviewer 优先攻击这五类（80% 的 P0 出自这里）：

| # | 攻击面 | 具体打点 |
|---|---|---|
| 1 | **分隔 / 切分边界** | 行尾、空单元格、最后一个字段、转义字符未 flush、连续分隔符 |
| 2 | **空与不存在** | 空文件、空表格、文件不存在、参数缺失、参数为 `-` 或空串 |
| 3 | **行尾与编码** | CRLF vs LF、BOM、UTF-8 多字节截断、中文路径、Windows 反斜杠 |
| 4 | **状态泄漏** | 多次调用间未重置的全局/缓冲；异常路径未清理临时文件 |
| 5 | **"看起来通过"的测试** | 只断言退出码不校验内容、硬编码期望值、测试里 `try/except: pass`、mock 掉了被测逻辑本身 |

附加常见坑：并发写同一文件、超长输入导致 O(n²)、浮点比较用 `==`、时间/时区、随机数未固定种子。

## 槽位 5 · 角色映射

| 通用角色 | 本领域角色 | 职责偏移 | 额外要求 |
|---|---|---|---|
| lead | 项目负责人 | 无 | 能判断"这是 S 还是 L" |
| spec | 需求分析师 | 把"好用/快"翻译成可观测指标 | 会写验收命令 |
| architect | 系统架构师 | 无 | 每个决策给"放弃项/理由/代价" |
| builder | 开发工程师 | 无 | 先写测试再实现，或至少 AC 全覆盖 |
| reviewer | 代码审查员 | 无 | **必须自己执行命令**，不许只读代码 |

## 槽位 6 · 附加合规

```
必须过的关卡：数据合规（个保法/GDPR，若处理个人信息）、开源许可证兼容性、等保（若涉政企）
谁签：法务 / 安全负责人
挂在哪个门禁上：G2（选型时确认许可证）与 G3（交付前确认无敏感数据硬编码）
```

## 槽位 7 · 判定用语

```
合格：`mdtable2csv nope.md` 退出码 = 2，stderr 精确等于 `file not found: nope.md`，无 Traceback
合格：1000 行输入下 P95 耗时 < 200ms（用 `time` 跑 20 次取 P95）
不合格：错误处理得当，提示友好
不合格：性能良好，响应迅速
本领域禁用语：健壮、优雅、高性能、可扩展、符合最佳实践
```

## 槽位 8 · 判级门槛

```
S：单文件、单函数、无接口变更、无新增依赖
M：单模块、有内部接口、或新增 1 个依赖
L：多模块 / 跨系统 / 新框架 / 涉及数据迁移
典型陷阱：改一个"配置项"看起来是 S，但它是全局开关 → 实际是 L
```

## 槽位 9 · 场景与规则包（v3 新增）

### 场景八槽位在软件域的映射

`scenario.md` 的 SC1–SC8 是通用工程槽位，软件要按下面重新解释 —— 照字面填"温度/腐蚀"会得到一堆 `N/A`：

| 槽 | 通用含义 | 软件域对应 |
|---|---|---|
| SC1 | 使用环境 | **运行环境**：OS / 运行时版本 / 终端编码 / 部署形态（本地/容器/Serverless） |
| SC2 | 介质与腐蚀 | **输入污染面**：非法编码、超长、注入字符、空值、异常格式 |
| SC3 | 载荷 | **数据规模与并发**：文件大小、行数、QPS、并发连接数、突发倍数 |
| SC4 | 寿命与维护 | 版本维护周期、依赖升级策略、向后兼容承诺 |
| SC5 | 安装与空间 | 依赖与安装方式、离线可用性、镜像体积 |
| SC6 | 法规与认证 | 销售地合规（个保法/GDPR）、行业准入（医疗/车规）、无障碍等级 |
| SC7 | 失效后果 | 数据丢失 / 越权 / 可用性中断 / 资损，是否安全相关 |
| SC8 | 量与成本 | 用户量、运维成本、云资源预算 |

### 默认规则包

| 场景标签命中 | 挂什么包 |
|---|---|
| 有认证/会话 | `example-sw-web-baseline`（ASVS V2/V3）或自建 |
| 有外部输入 | 同包 V5 输入校验 |
| 有部署 | CIS Benchmark 对应平台 |
| 车规/医疗 | ISO 26262-6 / IEC 62304（R0，必须挂） |

**软件的特殊性**：很多约束根本没有外部标准（"单文件无依赖""只用标准库"），
这类 DC 直接挂 `SC#` 即可，不必硬造一个 RULE。但**凡是数值型要求**（延迟、QPS、体积、覆盖率）
必须有出处，否则就是拍脑袋。

## 本领域的特殊提醒

**软件是唯一一个"验证成本近乎为零"的领域。** 这带来两个后果：

1. **好的一面**：可以高频验证，所以没有理由不写测试。
2. **坏的一面**：测试太容易写，于是大量测试是"装饰性"的 —— 跑得通、断言无意义。这正是槽位 4 第 5 条要专门攻击它的原因。

所以在软件领域，**审查者的核心任务不是找 bug，是找"假的绿"**。
